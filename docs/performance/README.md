# 性能测试与优化

本文件记录基准和优化的具体方法；长期工程约束见 [工程原则](../principles/engineering.md)。

## 当前交付状态

测试资源复用、无分配状态比较、DryRun 副作用修复以及 CI 调度/下载缓存已随主线提交 `c958d08` 合并。局部 `pvz-app` 测试取得同条件三次前后样本；workspace 总体和 CI 远端没有足够的同条件对照，不宣称全仓或 CI 墙钟收益。下一次优化必须重新建立同提交、同工具链、同 target、同 feature、同缓存状态和同 jobs 的有效基线，并先保护行为和回放合同。

按 [共同原则](../principles/README.md#共同原则)处理正确性、速度与内存取舍。先用单元、集成、边界和回放测试保护行为，再用可重复的时间与内存测量识别瓶颈；优化结论必须有测量和行为证据。开发与验证流程的速度按 [游戏开发效率原则](../principles/game-development.md#游戏开发效率)测量。

Criterion 基准放在拥有被测热路径的 package 的 `benches/` 中，使用固定 seed、明确输入规模、固定规则版本和资源无关的输入。说明初始化/预热与计时范围，区分波次总量、同时存活数量、调用次数和实际推进 tick 数；终局冻结不能被算成仍在执行完整规则更新。基准不依赖窗口、音频设备、用户目录或原版素材。

核心数据结构、解析与高频路径随实现建立代表性场景，优先复用已有基准，按行为或负载的覆盖缺口补充。变更重跑受影响场景；关键路径内存布局、分配策略变化，或声称内存改善时做对应测量，其他变更按性能影响与风险选择检查。

记录提交、工具链、硬件、编译配置、规则版本、输入规模、seed 和测量结果；比较时保持相同条件，测量期间避免其他测试或任务争抢资源。`cargo test --benches` 只检查基准目标能否执行，不代替性能测量。

优先测量：棋盘更新、碰撞候选、投射物处理、波次调度、资源索引查询、Reanim 采样和高分辨率视口变换。每次优化记录基准环境、输入规模、均值/离散度、行为测试结果和是否引入额外分配/复杂度。

内存优化按受影响路径测量峰值或稳态内存、堆分配次数和分配字节数等适用指标，注明统计范围、测量工具与版本、采样方式和预热条件。涉及 GPU 资源时单独记录纹理与缓冲的显存使用；进程内存、堆分配和显存采用各自的统计口径。Criterion 的计时结果只证明时间表现，内存改进须附对应测量。

比较优化前后时使用相同工作负载、缓存条件和生命周期阶段，并重复测量。时间与空间存在取舍时，在目标平台资源约束内优先满足速度目标，同时记录时间收益、内存代价和目标负载的选择依据；各平台分别记录结果及测量限制。

使用以下命令，按受影响场景筛选；提交验收流程见 [贡献指南](../../CONTRIBUTING.md#验证流程)：

```sh
cargo bench --workspace --locked
```

基准结果会随环境变化，不能把不同机器的绝对时间直接当作回归结论。性能优化不得改变状态摘要、事件顺序、回放结果或跨平台可观察行为。

## 开发反馈测量

开发流程调整记录“有效修改到首个相关结果”和“增量到适用验收完成”的耗时，并分别记构建等待、测试、覆盖率/基准、实际运行及人工步骤。明确提交或差异、工具链、target/feature、机器、缓存冷热和并发负载；只有相同工作范围、相同正确性门槛的重复比较才能声称提速。排队、工具不可用和目标平台等待单独记录，不能把未执行的必要检查从耗时中抹去。

计划中的双轨调度、检查复用和缓存隔离是减少等待与返工的设计，目前没有同条件开发耗时对照，不宣称具体速度改善。本节维护统计方法，具体执行读数进入相应任务结果和忽略的原始日志。

[七阶段计划](../superpowers/plans/2026-10-17-phased-development.md)将多项关联需求集中开发，随后统一实机测试与调整。评估该安排时分别记录开发/工程检查、打包启动、实机操作、缺陷修复与重测、环境等待的时间和重复人工步骤；比较必须覆盖相同需求及验收矩阵，不能把待验平台或未执行检查移出统计来制造提速。目前这是计划设计，没有同条件对照，尚不能声称开发耗时或内存已改善。

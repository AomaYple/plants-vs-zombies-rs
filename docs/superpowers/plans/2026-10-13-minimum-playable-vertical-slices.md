# 阶段性最小可玩垂直切片总计划

**状态：** 2026-10-13 仓库总览后重设；当前执行窗口为 S1，S2 是下一阶段，其余阶段维护目标和依赖。本文替代“原版行为测量是全项目唯一活动计划”的组织方式；已完成的工程计划和实测记录保留历史范围。

**目标：** 正确性第一、速度第二、内存第三。本轮优先减少游戏开发的等待、重复实现和返工，以连续的最小可玩版本逐步达到原版还原目标；每个阶段结束都能从正常入口完成一段玩法，保留之前已交付的可玩流程。

**架构：** 沿用现有五包，不重建 workspace。`pvz-data` 表达版本化内容，`pvz-core` 执行确定性规则，`pvz-assets` 解析资源 CPU 模型，`pvz-app` 通过 Bevy 装配输入、时钟、表现与平台，`pvz-asset-tool` 审计资源。规则、资源和平台之间的依赖方向保持不变。

**技术栈：** 以 `rust-toolchain.toml`、`Cargo.toml` 和 `Cargo.lock` 为准；当前 Rust 1.99.0、Edition 2024、Bevy 0.20.0。复用 serde/serde_json、quick-xml、image、Criterion、cargo-llvm-cov、cargo-deny 与现有 GitHub Actions，不为规划预建依赖、通用框架或空模块。

**设计依据：** [总体设计](../specs/2026-10-07-repository-and-runtime-design.md)、[版本化内容设计](../specs/2026-10-12-versioned-day-content.md)、[行为测量设计](../specs/2026-10-12-reference-behavior-measurement.md)、[项目原则](../../principles/README.md)。具体执行依照项目协作和验证流程，任务用复选框追踪。

## 全阶段完成合同

长期质量约束以[工程原则](../../principles/engineering.md)和[游戏开发原则](../../principles/game-development.md)为准；本节定义可玩阶段的验收，不复制工具链和全量命令矩阵。

每个新阶段及独立子阶段必须同时满足：

1. **能进入：** 从正常应用入口加载清单资源和明确版本的内容；无原版程序运行依赖，不靠调试器、手工内存修改或隐藏状态注入形成玩法。
2. **能玩完：** 有具体起点、玩家操作、目标、结果和重试/返回路径。战斗阶段至少验证一条正常胜利和一条正常失败路径；工具/平台增量复用此前完整关卡，不能只交付探针。
3. **能解释：** 数据、core、输入、画面、音频和结果同属一个合同；开发参数、原版观察与推断、静态/测试/真实运行分别记录。已有证据的范围不能扩大。
4. **能回归：** 随实现交付适用的单元、集成、边界、错误、确定性回放、平台或端到端测试；默认并行并隔离状态。优先补关键缺口，不靠冗余测试或改分母提高覆盖率。
5. **能测量：** 新规则、解析和热路径有相关可重复时间基准；内存布局/分配策略变更或内存改善主张增加测量。比较使用同条件输入与版本，行为正确性先于提速。
6. **能交付：** 阶段范围有 Windows/Web 实际关卡证据，受影响的已验收平台同步回归；目标六平台的静态与实跑状态分开。编码、来源、卫生、适用本地检查和 CI 通过，一个完整目的一个中文 Conventional Commit，可独立回退。

正常玩家场景与加速自动测试夹具分别登记。测试夹具可快速验证失败分支，但单靠夹具通过不能把默认关卡或整个阶段写成已验收。正常关卡中的相应路径仍需实跑。

## 速度与风险安排

- **近期细化、远期按目标规划：** 本轮只把 S1 展开成可执行任务，S2 锁定首个资源消费者。开始后续阶段前根据新证据细化该阶段的文件、场景、接口和检查，提交可审阅的计划更新再实施；不提前猜测未确定规则或创建新 package。
- **一条主线、一个主动增量：** 优先闭合当前可玩阶段；独立原版测量、只读调查或已隔离检查可并行。共享 checkout 的修改、Git、安装和服务统一协调，不让并发构建争抢同一个 target；基准独占。
- **纵向交付：** 数据、规则、输入、表现、测试和结果一起进入小提交；不连续数阶段只做 core 或资源系统。复用现有 JSON 装配、PreparedAnimation、视口和回放，只有真实重复消费证明抽象有收益才扩展。
- **短反馈与完整收口：** 开发中先检查受影响 package/场景，提交前完成全部适用门槛。相同实现的有效历史验证可引用；新修改或失败使相关证据失效，不为提速跳过必要检查。
- **环境阻塞局部化：** 原版或目标设备不可用时登记影响与恢复条件，继续不依赖它的独立工作；必要实际运行缺失的阶段保持“待验收”，不改写为完成。后台运行优先，最小必要前台范围说明原因。
- **不预承诺工期与优化收益：** 没有同条件测量不声称具体提速；阶段按可玩结果而非代码量判断，必要质量工作归入该阶段。

## S1：可靠的白天单关

**玩家闭环：** 启动白天开发关卡 → 选择两卡、种植/收集/铲除 → 攻击/割草机/波次 → 胜利或失败 → 状态与动画冻结 → 重开回到同一初始合同，再次正常种植。暂停与恢复可穿插于运行中。

**当前缺口：** 默认内容无种植曾得到胜利，不能假定等待就会失败。core 已有胜负回放，app 现有终局测试主要覆盖胜利；浏览器失败和后续恢复仍未收口。shader 的间歇性 unresolved-import 诊断保持可见；若影响阶段绘制先修复，若不影响则记录复现范围和影响证据。

- [ ] 每个子增量均实跑 S1 成功/失败并核对 core 摘要/事件不变；采用明确开发动画时基，未测插值/混合语义保持未知。性能测量区分 CPU 采样、构图和 GPU 帧耗时，避免每帧重新解析/上传全部资源。

**完成定义：** 两个已选对象在完整关卡中提供必要动态反馈，暂停/终局/重开一致；任一子阶段已单独交付可玩版本，规则回放不因表现替换改变。S2 不是全部原版动画验收。

## S3：新策略和两关白天冒险

**玩家闭环：** 从最小菜单选择/继续游戏 → 选卡玩第一关 → 解锁并玩第二关 → 保存 → 退出/再启动继续；失败可重试当前关，不误推进关卡或奖励。

**内容顺序：** 先增加坚果这一防守策略并交付一关，再增加路障僵尸及护甲交互并交付下一关，最后连接两个已验收场景。生命、费用、护甲消耗等依据合格证据或显式开发合同；不预建所有植物/僵尸的全集 schema。

**范围与验证：** 按消费者扩展 data/core 和 app 卡片/表现，建立新策略成功、资源不足、破坏/死亡、护甲命中和重开回放；第二关引入可解释波次节奏。进度 DTO 严格版本化，文件/浏览器存储放 app 适配；成熟存储能力满足平台合同时优先复用。

**性能与平台：** 多类型碰撞/波次和小存档解析基准；Windows/Web 真实选卡、两关结算、保存恢复与损坏/未知版本存档验收。macOS/Linux 最迟本阶段补实际窗口关卡证据；目标环境不可用则保持平台待验，同时可交付已验环境。

**完成定义：** 新策略参与正常玩法，连续两关及保存继续形成闭环；菜单不是纯展示，存档不是无消费者文件；没有为将来模式预建空实现。Android/iOS 在此阶段开始构建与最小启动风险探针，正式可玩验收仍由 S7 管理。

## S4：每种环境一个可玩关卡

四个子阶段分别交付，顺序为夜间 → 泳池 → 雾 → 屋顶；每次保留 S3 白天冒险回归，不等全部地形写完才连接 app。

| 子阶段 | 最小场景与玩家闭环 | 新规则与完成证据 |
| --- | --- | --- |
| S4-A 夜间 | 选取蘑菇/夜间卡组、防守、处理一个墓碑相关场景并结算/重试 | 夜间阳光与蘑菇/墓碑作用分别标来源；种植、伤害、目标顺序回放 |
| S4-B 泳池 | 荷叶与水上种植、陆水两路防守、完整胜败/重开 | 地形兼容、承载/移除和跨路隔离；错误种植及视觉/点击一致 |
| S4-C 雾 | 进入有雾场景、使用一个有效视野策略、防守并结算 | 雾只遮挡表现还是影响规则依据合同明确；视野操作与命中/输入不混用 |
| S4-D 屋顶 | 花盆和最小抛投策略、防守屋顶关卡、结算/重试 | 花盆承载、坡面/抛投及坐标合同；高分辨率输入仍不改变碰撞 |

每个子阶段只引入让该场景成立的最少植物、僵尸、地形数据和图形/音频；随实现新增边界/错误/回放及对应热路径基准，Windows/Web 完整关卡实跑。适用 macOS/Linux 同步回归。未验收的环境仍未支持，不能用一张背景表示完成。

## S5：冒险通关闭环

**玩家闭环：** 从已有进度依次进入已交付场景 → 完成必要解锁 → 遇到一个可玩最终遭遇 → 通关展示 → 继续/重玩；失败回到当前关并保持合法进度。

**进入与范围：** 前置环境与攻击类型已有可玩证据后，先完成最小首领/阶段转换和通关流程，再按独立关卡扩展冒险。暂用少量关卡连通时标记为开发冒险，不能称为完整原版冒险。

**验收：** 解锁、奖励、防重复发放、首领阶段、失败、退出/恢复和存档版本回归；首领/多波热路径基准；真实完整通关和失败继续。完整关卡集合仍由 S8 补齐，旧开发进度的兼容/拒绝策略显式记录。

## S6：每个附加模式一个完整小场景

| 子阶段 | 最小可玩交付 | 验收重点 |
| --- | --- | --- |
| S6-A 小游戏 | 单个保龄球关卡，从模式选择到投放/碰撞、结算和返回 | 使用玩法专属规则，输入、弹道、碰撞顺序和重开 |
| S6-B 生存 | 两轮白天防守，轮间重新选卡并继续，失败或第二轮完成后返回 | 跨轮保留与重置状态、奖励边界、保存/继续 |
| S6-C 谜题 | 单个砸罐子场景，揭示内容、执行行动、胜败和重开 | seed/隐藏内容、揭示顺序、输入边界和回放 |
| S6-D 禅境花园 | 一盆植物的照料、奖励、退出/恢复 | 与纯战斗 tick 分离的显式时间输入、重复领取、存储边界 |
| S6-E 图鉴/商店 | 查阅已使用角色，完成一次有来源的购买/解锁，再在已完成关卡中使用 | 余额、重复购买、解锁/存档、返回正常玩法 |

只为选定场景引入实际数据和表现，模式从主菜单进入且可返回，不一次实现全部模式框架。每个子阶段独立满足全阶段合同，新增规则或解析有基准；原版仍待证据的参数继续标开发来源。其他小游戏、生存/谜题场景和花园内容逐批由 S8 扩展。

## S7：Android/iOS 各一条可玩平台闭环

S7-A Android、S7-B iOS 分别验收，复用 S3 或之后已完成的同一关卡与数据版本：安装/启动 → 触摸选卡和种植 → 胜败/重开 → 后台/前台恢复 → 保存 → 再启动继续。

不把移动端留到最后才评估：S1/S2 修改时核对六平台依赖与时钟/输入边界，S3 开始移动构建/启动探针。有可用环境且收益明确时提前完成平台子阶段；不能编造 Android/iOS 入口或把 Windows 构建当作实机证据。

**验收：** 分别记录应用入口、资源包、数据目录、触摸/安全区/尺寸、音频、生命周期中断、帧时间/内存与打包；iOS 需要 macOS/Xcode 和目标运行环境。更换平台适配不改变 core 摘要/事件。设备或签名条件缺失时登记阻塞，已完成其他平台继续可玩。

## S8：在可玩版本上逐批补全原版

每批是一关或一个模式的小内容组，包含真实玩法消费者和完成场景。逐类补齐剩余植物、僵尸、特殊交互、冒险关卡、小游戏/生存/谜题/花园，完善 idle/攻击/受击/死亡混合、粒子、菜单/UI、音效和音乐。

MO3 解包/播放先评估成熟库、许可、维护和六平台兼容性，在一条已完成关卡中验证实际播放、循环、暂停、重开与资源卸载，再扩展曲目；OGG 探针不能替代 MO3 验收。高清适配保持逻辑坐标/碰撞，用实际视口绘制；DPR 2/4、真实触摸和更多浏览器补实证，不把放大低清素材称为增加细节。

**完成定义：** 当前可玩回归集合持续通过；每个被声明还原的规则和表现有适用证据、误差与版本，完整内容/模式清单逐项对照参考范围。只补必要 schema/格式，不在没有合格证据时把整个关卡 `basis` 改成已测。按受影响已支持平台验证，性能和覆盖缺口与内容同步闭合。

## S9：逐平台发布仍可玩

**玩家闭环：** 从干净安装包或 Web 部署入口启动 → 进入已完成关卡/模式 → 胜利或失败 → 保存进度/设置 → 退出再启动恢复；更新版本时使用明确迁移/拒绝策略。

Windows、macOS、Linux、Web、Android、iOS 分别登记构建、真实运行、输入、生命周期、音频、存档、资源安装路径、性能预算和打包证据；六平台全部闭合才称全平台发布。Web 验证发布目录而非开发根目录服务，桌面验证安装后目录，移动验证实际应用资源包。

**完成定义：** 完整目标内容与还原证据清单闭合；UTF-8/LF/无 BOM、无死代码/无用文件依赖、来源指纹、原创 MIT 与原版/第三方资源许可边界通过公开发布检查。原版 EXE、录像、截图、存档和临时派生物不进入 Git/CI/发行包；代码与资源包的实际发布按授权执行，不因计划完成自动发布。

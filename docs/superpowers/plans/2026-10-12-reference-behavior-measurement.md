# 原版行为测量与并行开发专题计划

> 横向证据专题计划，调度入口于 2026-10-17 更新。全项目阶段见[七阶段总计划](2026-10-17-phased-development.md)，当前开发见[第一阶段计划](2026-10-17-phase-1-day-combat.md)；本计划只管理原版测量、证据采纳和相应回归。旧 D1/D2、S1/S2 的历史移交记录保留，当前任务在新阶段计划维护。

## 目标

在不把未测行为写成规格的前提下，用一个可重复的端到端案例验证测量入口，再按案例依赖取得证据并替换开发参数。原版测量受阻时继续推进有明确开发合同的独立任务；证据充分的参数及时交付，不等待无关案例。每个增量独立验收、独立回退，缩短等待和返工周期。

交付结果必须能回答五个问题：参考程序和资源是否仍是同一组文件；观察是否由固定输入和连续画面支持；结论属于观察、推断还是开发参数；哪些开发工作可以在证据阻塞期间继续；被采纳的规则是否有核心回放、回归测试和必要的性能证据。

## 架构

证据与开发分轨推进，规则采纳保持单向：

```text
证据轨：参考身份 → 可靠窗口入口 → 三次教程重复 → 按案例测量
                                                    ↓ 达到对应接受条件
规则采纳：参数来源与版本 → 核心回归/逐 tick 回放 → Bevy 表现验收
开发轨：阶段需求与合同 → 集中开发并持续自动化 → 工程检查 → 集中实机与调整
```

原版 EXE 只提供资源输入和可观察行为参考，不进入生产运行依赖。`pvz-core` 继续保持纯 Rust，不依赖 Bevy、资源解析、操作系统 I/O、设备输入、音频、资产路径或墙钟时间；规则替换先更新数据和核心合同，再由 `pvz-app` 消费状态与事件。

## 工具链

- Rust stable 1.99.0、Cargo workspace、现有 `pvz-data`、`pvz-core`、`pvz-assets`、`pvz-app` 与 `pvz-asset-tool`。
- Bevy 负责应用表现和平台接线；规则、回放和资源模型保持引擎无关。
- Windows 原版窗口用于参考观察；本机原始帧、录像、存档、窗口元数据和临时脚本写入被忽略的 `artifacts/` 或仓库外。
- 现有 Cargo 测试、覆盖率和 Criterion 基准作为验证入口。只有出现稳定消费者且能减少重复工作时，才引入新的测量辅助工具、数据格式或 package。

## 记录规范

设计和完整记录合同见[行为测量设计](../specs/2026-10-12-reference-behavior-measurement.md)，已有案例与阻塞见[参考基线](../../behavior/reference-baseline.md#2026-10-13-首个端到端案例登记)。

每个案例使用唯一 `case_id`，至少包含 `reference_id`、场景和初始状态、输入序列、观察窗口、有效/失败重复次数、可见事件、误差、分类和接受条件。分类固定为 `observed`、`inferred`、`development_parameter`；帧率不能直接当作模拟 tick 频率，区间和离散顺序必须保留。

首个端到端案例固定使用已证实可进入的冒险 1-1 教程种植动作：核对目标 EXE 与 `main.pak`，绑定目标进程，确认连续画面，执行相同输入，至少取得三次有效重复，建立本机原始证据索引，并把结果以中文文本追加到现有行为基线。这个案例首先验证测量链路的可靠性，不提前声明时基、碰撞或其他规则。

## 全局约束

- 正确性第一、速度第二、内存第三；速度包括运行速度和开发迭代速度。任何提速都必须保留行为、事件顺序、回放和平台合同。
- 原版程序不作为运行依赖；原版截图、录像、存档和临时脚本不进入 Git、CI 或发行包。版本化参考资源仍由清单和指纹管理。
- 所有公开文本使用 UTF-8、LF、无 BOM、末尾换行；新增文件、目录、工具和字段必须有实际消费者。
- 测量和窗口交互尽可能后台运行。窗口捕获与输入保持局部串行，已生成的帧、日志和元数据整理可以并行；不同 package 的纯测试可以并行；性能基准独占构建和运行资源。
- 未达到接受条件的结果继续标为未知、推断或开发参数，不批量改写规则来源，不以最终胜负相同替代逐 tick 状态与事件比较。

## 调度与阻塞处理

| 任务 | 必要前置 | 可以同时推进的工作 | 完成边界 |
| --- | --- | --- | --- |
| 任务 1 记录合同 | 已完成 | 后续任务的静态准备 | 案例登记，不能算重复测量 |
| 任务 2 教程重复 | 可用的原版窗口、固定初始状态 | 当前阶段集中开发；资源静态准备 | 三次独立有效重复 |
| 任务 3 规则测量 | 任务 2 通过；各案例自己的场景/时间/位置条件 | 已合格案例的任务 4；总计划后续阶段 | 按案例接受，未知项继续未知 |
| 任务 4 规则采纳 | 对应案例合格及单位/范围可表达 | 无关案例测量与独立开发 | 单参数或紧密规则组的来源、版本、回归与平台验证 |
| 现有白天单关基线 | 旧 S1/S2-A 已交付；B1 工程范围已完成 | 原版证据轨仍独立维护 | 历史事实保留，B1 待验迁入阶段 1 |
| 阶段 1 完整战斗体验 | 现有可玩单关、可靠状态/事件和资源消费者 | 原版测量和无依赖的开发任务 | 集中开发动作/反馈，统一工程检查、Windows/Web 实机与调整 |
| 任务 5 收口 | 一个完整增量通过适用验收 | 下一独立任务的准备 | 交付该增量；整体计划仍保留未完成项 |

证据轨按案例直接依赖推进，开发轨按当前阶段集中完成关联需求。缺少原版窗口不阻塞有明确开发合同的独立工作，缺少阶段实机证据也不能宣称阶段完成。同一 checkout 的写入、Git 操作与外部状态统一串行协调，并行只用于已隔离的任务、输入、证据处理和检查。

窗口入口先确认当前会话提供目标应用清单、绑定、输入与连续捕获能力，再启动参考程序。能力明确缺失时不反复启动；同类失败只有在工具、窗口状态或输入条件有新证据变化时才重试。阻塞记录写明失败环节、影响任务、可继续工作和恢复条件；清理自有进程，转入独立任务。

## 开发反馈分层

根据变更风险选择最低足够层级，并在提交前升级到所有适用门槛：

- **L0 文档与结构反馈**：差异、编码/资源边界、文档链接和 `cargo metadata --no-deps --locked --format-version 1`。
- **L1 受影响 package 反馈**：格式、受影响 package 的测试和 Clippy；只验证当前改动能影响的 target，保持短反馈。
- **L2 行为与性能反馈**：规则、解析、回放或热路径变更时，运行受影响覆盖率、回放回归和基准；基准期间不并行启动其他构建、测试或窗口进程。
- **L3 提交与远端验收**：按贡献指南完成全部适用 L0/L1/L2；Rust/依赖/构建变更追加 workspace、兼容 feature、文档和依赖审计，再核对提交、推送和远端 CI。纯文档更新按 L0 收口。

命令、隔离和重复检查的具体规则统一见[贡献指南](../../../CONTRIBUTING.md#反馈层级)。计划不复制全量命令矩阵。测试默认并行，避免多个 Cargo 进程争抢同一构建目录；性能基准独占资源。没有新修改或未解决问题时，不反复运行已通过且与当前状态匹配的检查。开发速度的测量方法见[性能策略](../../performance/README.md#开发反馈测量)。

## 任务 2：完成首个端到端案例

**文件：** `docs/behavior/reference-baseline.md`、`docs/behavior/README.md`；原始记录写入被忽略的 `artifacts/validation/reference-behavior-*`。

- [ ] 先确认目标窗口控制与捕获能力可用；运行前核对 EXE、`main.pak`、仓库清单和指纹，记录环境与进程。每次重复独立核对窗口、DPI、输入设备、初始状态及引用的身份报告；输入文件变化时重新核对完整指纹。
- [ ] 先确认连续画面和固定输入能够到达同一教程状态，再执行 `tutorial-plant-01`；后台启动优先，前台操作只用于窗口接口无法后台完成的步骤，并记录原因。
- [ ] 在第一次有效重复前锁定选卡区域、合法种植位置、客户区坐标、按下/释放、等待条件与观察终点；记录所用正常游戏操作如何重建同一新用户教程状态。无法重复建立初始状态时继续记为阻塞，不编辑存档制造场景。
- [ ] 至少取得三次独立有效重复，分别保存输入序列、原始帧号/时间、失败重试、捕获误差和环境元数据；每次完成后立即核查有效性，失败单独记录，不用退出码代替画面证据。
- [ ] 只有字段完整且证据可索引时才把结果追加到公开基线；入口不稳定时记录阻塞和影响范围，修复入口后再扩展测量面。

**验证：** 主代理核对每次运行的指纹、重复次数、证据索引和结论分类；清理无索引临时产物与本次启动的进程。

## 任务 3：按案例依赖测量动态规则

**文件：** `docs/behavior/reference-baseline.md`、`docs/behavior/README.md`，必要时更新现有设计中的案例依赖矩阵。

- [ ] 任务 2 通过后，优先采集可直接观察的阳光、攻击和啃食间隔；每个案例至少三次独立有效重复。时基作为独立候选模型测量，无法由画面唯一识别时保持未知，不阻塞其他可见事实的记录。
- [ ] 依据设计中的依赖矩阵选择命中、碰撞和顺序案例；不要求无关的间隔案例全部合格。只有画面分辨率能约束的区间或顺序才形成结论，不能将推断标为内部算法事实。
- [ ] 具备场景与控制条件后即可测量波次、胜负、暂停/恢复和重开，不等待无关碰撞案例；终局画面、冻结和重开分别记录。开发单关的历史验收及阶段 1 回归不能混入原版证据。
- [ ] 公开结果逐项列出已测量、候选推断、开发参数、未知项、重复次数、误差和下一步，不创建通用 CLI 或持久回放格式来替代真实消费者。

**验证：** 每个案例结果完成后执行 L0；对应证据、单位、适用场景和误差均满足接受条件才进入任务 4，其他案例继续保持未完成。

## 任务 4：一次只采纳一个参数或紧密规则组

**文件：** `content/levels/development-day.json` 或有实际消费者的新内容、`crates/pvz-data/src/day.rs`、`crates/pvz-data/tests/day_content.rs`、`crates/pvz-core/src/content.rs`、`crates/pvz-core/tests/day_content.rs`、`crates/pvz-core/tests/determinism.rs`、`crates/pvz-app/tests/day_content.rs`、行为基线与开发切片合同。

- [ ] 先核对案例适用场景、数值单位与核心表达能力；不能把教程初始阳光推广到全部关卡，也不能在未知时基下把秒数无依据地转成原版 tick。不能准确表达时保留候选结果，先设计必要的时钟或规则合同。
- [ ] 首次采纳前解决来源格式：当前 `ContentBasis` 只有 `Development`，JSON 仅支持整个定义的 `basis: development`，core 仅接受规则 2.0。为实际参数消费者设计逐字段/规则组的来源与案例索引、schema/规则版本、兼容或拒绝策略，先补未知来源、缺失证据和旧版本回归，再实现严格解析与装配；不得把部分实测的关卡整体标为已测。
- [ ] 每次只采纳已合格的一个参数或紧密规则组，保留其他字段的开发来源；证据来源本身仍分类为 `observed` 或 `inferred`，采纳状态单独记录。没有合格参数时不预建来源框架。
- [ ] 若 tick、间隔、碰撞或阶段顺序改变，先更新规则/内容版本和来源，再更新装配边界、无效输入处理和回放兼容/拒绝策略。
- [ ] 为每个替换参数补充正常、边界和错误回归；用固定输入比较逐 tick 状态摘要与事件序列，不能只比较最终胜负。
- [ ] 先运行受影响 package 的 L1 检查，再运行相关覆盖率和 Criterion 基准；性能结果与行为结果分开记录，优化不能掩盖规则变化。

**验证：** data/core/app 受影响测试、逐 tick 摘要与事件回放、相关覆盖率和基准；每个可交付参数增量执行适用 L3，不等待其他规则批次。

# 七阶段集中开发总计划

> 执行说明：当前阶段按对应实施计划推进；需要执行技能时使用 `superpowers:executing-plans`。主代理统一整合和验收，委派按项目规则判断。

日期：2026-10-17；更新：2026-10-18
状态：工程维护已交付并核验主线；阶段 1 待启动，任务与依赖见第一阶段实施计划。

**目标：** 每阶段集中完成多项关联需求，再集中实机测试与调整，持续交付完整可玩版本。

**架构：** 沿用现有五包及 data → core → app 装配关系；assets 提供独立 CPU 资源模型，app 负责平台与表现。新增能力由实际玩法消费者驱动，模拟状态和事件决定规则。

**工具链：** Rust、Cargo、Bevy 和依赖版本以根 `rust-toolchain.toml`、`Cargo.toml`、`Cargo.lock` 为准；不因重排计划升级依赖或改变 CI。

**设计：** [阶段开发设计](../specs/2026-10-17-phased-development-design.md)；长期约束见[项目原则](../../principles/README.md)，操作见[贡献指南](../../../CONTRIBUTING.md#阶段开发与集中实机验收)。

本计划维护全项目阶段、依赖和完成标准；[第一阶段实施计划](2026-10-17-phase-1-day-combat.md)维护当前任务。后续阶段进入实施前再制定详案，结果写入已有行为结果页，路线图和 README 只保留摘要。

当前已有白天单关、双终局、暂停/恢复、重开、向日葵 idle 与普通僵尸 walk。旧 S1、S2-A 已交付；B1 工程实现与部分 Web 证据已取得，Windows 正常窗口缺项和 Web 诊断仍开放；B2 可靠啃食/死亡尚未实现。测试优化和规则整合已交付。原版有效重复仍为 `0/3`，当前数值属于明确开发合同。

已核验的维护提交、PR 和主线 CI 统一见[仓库整理记录](2026-10-18-repository-cleanup.md#已核验的主线交付基线)。维护事项已收口，后续产品开发从阶段 1 任务 1 的可靠观察合同开始；任务依赖、现有测试入口和待验边界由第一阶段详案维护，不另设维护阶段或第二份当前待办。

阶段状态使用：待启动 → 集中开发 → 工程检查 → 实机测试与调整 → 验收交付。每个状态分别记录结果；工程检查失败退回开发，实机问题修复后复验受影响范围。缺少必要环境时写明平台待验，不勾选阶段完成。

## 通用阶段合同

- 范围确定时列出必做、可延后、真实依赖、受影响平台和验收场景。阶段内连续完成多个需求，调整范围须保留原因与原有未完成项。
- 自动化验证随开发持续进行，规则、解析和热路径同步接入覆盖率、回放及代表性基准。实机集中验收安排不降低提交与 CI 门槛。
- 待测版本固定代码、资源、内容、工具链和 target/feature 身份；同一次有效运行可覆盖多个场景。新修改使受影响证据失效，修复后重新检查。
- 阶段完成须有正常入口、玩家操作、可观察结果和重试/返回；战斗阶段覆盖正常胜利与失败、暂停、终局冻结、重开和原有流程回归。
- Windows/Web 为近期必需实机验收；其他平台按下表推进并单独报告。原版未知项只阻塞对应规则采纳，不能由开发参数、截图或 CI 替代。
- 阶段可由多个完整目的提交/PR 组成，每个合入满足适用验证；主线保持可构建、可测试和已有可玩流程。阶段总状态在必要实机验收与 Git/CI 收口后更新。

## 阶段 1：完整白天战斗体验

**玩家目标：** 从现有入口玩完白天关卡，清楚看到植物发射、命中/受击、僵尸行走/啃食/死亡、植物被移除及胜败结果，暂停和重开保持一致。

**集中开发范围：** 可靠攻击者/目标与死亡锚点、动作状态与时钟、现有两植物和普通僵尸的必要反馈、既有音效对应、UI 与输入状态、缓存和回归。只增加本关实际消费的能力，不扩展完整混合播放器或全资源粒子系统。

**实机与完成标准：** Windows/Web 在同一待测版本覆盖正常胜败、行走转啃食、目标消失后恢复、死亡残留清理、暂停恢复、终局冻结、重开、resize 和诊断；补齐 B1 无遮挡动态图及 Web 日志缺项，实际检查本阶段音效。未取得设备音频证据时保持待验，不把映射测试视作实听。

- [ ] 按[第一阶段实施计划](2026-10-17-phase-1-day-combat.md)完成整批开发、工程检查、集中实机调整和交付。

## 阶段 2：白天冒险与进度

**玩家目标：** 选卡进入至少两关，使用新策略通关解锁，失败重试，退出后继续已有进度。

**集中开发范围：** 在既有两植物/普通僵尸上增加坚果和路障僵尸，连通防守、护甲、卡片/表现及波次；实现有实际消费者的菜单、选关/选卡、结算、解锁和版本化存储。内容扩展只围绕本阶段选定关卡，未知数值继续标记开发依据。

**实机与完成标准：** Windows/Web 连续两关及退出重启恢复；覆盖资源不足、卡片冷却、防守破坏、护甲移除、死亡、失败不误解锁、坏存档和未知版本处理。macOS/Linux 做对应窗口关卡复核；Android/iOS 检查构建和最小启动、存储接口风险，缺环境记录恢复条件，不声称移动可玩完成。

- [ ] 启动时基于阶段 1 实际接口确定文件与关卡批次，完成上述开发、自动化、集中实机和交付。

## 阶段 3：夜间与泳池

**玩家目标：** 在同一冒险入口进入夜间和泳池关卡，使用环境对应策略，完成胜败、重试与保存继续。

**集中开发范围：** 夜间阳光/蘑菇等实际选定机制，泳池陆水格规则与水上承载，所需植物/敌人、场景表现和代表性波次。选择的角色集合在启动时登记，不提前构建全集 schema。

**实机与完成标准：** 两种环境各至少一条完整关卡；验证陆水合法位置、昼夜差异、对应战斗交互、保存/重开和白天回归。必要平台与输入变化同步回归，环境音画及资源错误有实际检查。

- [ ] 按环境依赖完成关联需求后集中测试两种环境，修复并交付可继续的冒险版本。

## 阶段 4：雾、屋顶与冒险通关

**玩家目标：** 从已有进度经过特殊环境到最终遭遇，通关或失败重试，退出后恢复正确进度。

**集中开发范围：** 雾的可见性、屋顶地形和种植/投射物交互、必要角色与关卡、最终战和通关结算；复用已有选卡、存储和战斗系统。

**实机与完成标准：** 雾、屋顶各有正常可玩关卡；最终遭遇包含正常胜败、重试和通关保存。测试遮挡与命中不混淆、地形输入正确、跨关进度不损坏，并回归已交付环境。

- [ ] 完成环境与最终战整批开发，集中游玩从已有进度到通关的路径并交付。

## 阶段 5：附加模式与外围系统

**玩家目标：** 从正常菜单进入模式、完成目标并结算返回；图鉴、商店和花园服务已实现内容和进度。

**集中开发范围：** 保龄球等小游戏、生存、砸罐子等谜题、禅境花园、图鉴/商店及奖励关联。启动时按共享规则和存储依赖确定有限批次，每批集中完成多项关联需求再实机验收，完整模式清单由参考范围核对。

**实机与完成标准：** 每个纳入批次的模式均有进入、操作、结果、重试/返回和保存路径；奖励不重复发放、商店消费失败不扣款、图鉴与实际内容一致，并回归冒险存储。整阶段完成须覆盖已登记的全部批次，不能仅凭一个示例模式关闭。

- [ ] 登记模式范围与批次，逐批集中开发/实机调整，最终检查所有模式入口与共享进度。

## 阶段 6：内容补全与还原调整

**玩家目标：** 已有可玩模式具备参考范围内的完整内容和连贯视听体验，已声明还原的行为能够追溯证据。

**集中开发范围：** 对照参考范围补剩余角色、关卡、模式、动作、必要插值/混合、粒子、UI、音效和音乐；评估 MO3 的成熟方案、许可和六平台适用性，完成实际播放/循环/暂停/卸载后扩展曲目。采纳已达接受条件的规则并维护版本及兼容策略。

**实机与完成标准：** 内容清单逐项核对；原版测量按案例接受，未知项不计还原完成；检查长时间玩法、音频、动作、资源释放和代表负载。高分辨率保持逻辑坐标/碰撞，核对真实 DPR 2/4、触摸和更多浏览器，画面放大不能冒充新增细节。

- [ ] 在持续证据采集基础上完成内容差异、规则回归和集中实机对照，关闭声明范围内的缺项。

## 阶段 7：六平台适配与发布

**玩家目标：** 在 Windows、macOS、Linux、Web、Android、iOS 安装或打开发行版本，正常游玩、保存并在退出或中断后继续。

**集中开发范围：** 完成前期探针暴露的图形/音频/输入/存储适配、触摸与安全区、后台恢复、设备中断、分辨率和资源预算；构建各平台安装/部署包并检查资源与许可边界。

**实机与完成标准：** 每个平台分别验证安装/加载、关卡与模式、保存重启、生命周期、音频、帧时间/内存和必要权限；iOS 需要 macOS/Xcode、签名及目标环境。平台之间不互相代验，任何必要平台缺环境时保持该平台及整阶段待验。

- [ ] 完成六个平台各自的开发、实机修复、发布包复核与交付，最后核对全项目范围。

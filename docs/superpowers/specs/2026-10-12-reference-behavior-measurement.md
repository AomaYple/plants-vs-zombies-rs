# 原版行为基线测量设计

日期：2026-10-12。本文定义已核对 EXE 与 `main.pak` 的可观察行为测量边界，为开发切片提供可追溯的规则证据；它不把原版程序作为项目运行依赖，也不改变 Rust 重写的 clean-room 实现边界。

## 目标与边界

当前重写已经有可玩的白天开发切片和版本化原创 JSON，但其 60 tick/秒、间隔、碰撞盒和阶段顺序仍是开发参数。下一阶段只测量能由原版窗口、输入和连续画面可靠观察的事实，并把足够重复的结果转换为规则合同与回归案例。原版内部 RNG、私有事件和不可见状态只能标为推断，不能由截图直接声称已知。

测量目标按以下顺序推进：目标版本身份与窗口资格、逻辑时间节奏、阳光/攻击/啃食间隔、投射物命中和碰撞边界、波次与胜负边界、暂停/失焦/重开。完整内容、动态动画、MO3、移动平台和发布打包不属于本设计的完成条件。

## 开发效率与反馈分层

测量按“先入口、后规则、再扩展”的顺序推进。先完成一个已能进入的冒险 1-1 教程种植案例：确认文件身份、连续画面、固定输入、三次有效重复、原始证据索引和公开文本结果。这个闭环通过后，才扩展到时基/间隔、碰撞/事件顺序和终局/暂停/重开；每一批都有自己的接受条件，入口失败时不继续积累更大范围的捕获。

开发反馈按风险分层：文档和结构改动使用 L0；局部 Rust 改动优先使用受影响 package 的 L1 测试与 Clippy；规则、解析、回放和热路径改动追加 L2 覆盖率、回放回归与基准；提交前按贡献指南完成 L3 workspace 与远端验收。不同 package 的纯测试可以并行，原版窗口启动、输入和捕获保持局部串行，已产生的帧、日志和元数据可以并行整理，性能基准必须独占构建与运行资源。

不因为追求短反馈而降低正确性门槛；选择较低层级只表示当前改动不影响更高层级的合同。只有重复出现且已有稳定消费者的步骤，才值得引入后台工具或数据格式；不预建通用 CLI、持久回放格式或新的 package。

## 参考身份与控制变量

每组记录必须包含参考基线 ID `goty-zh-a7ab7df8-7f1e824e`、EXE 与 `main.pak` SHA-256、操作系统、窗口尺寸、显示缩放、输入设备、关卡/用户状态和采集日期。测试使用同一目标进程和同一资源状态，输入序列、初始状态、观察时长与录制帧率固定；改变变量时新建独立案例并说明原因。

原版截图、录屏、存档、窗口元数据和临时脚本写入被忽略的 `artifacts/` 或仓库外，不进入 Git、CI 或发行包。公开文档只保留可复核的文本结果、参数表、误差和证据索引。一次观察只能证明一次观察到的范围；至少三次独立重复才能作为候选稳定事实，随机或边界行为需要更多重复和明确的离散结果。

## 测量记录合同

每个案例使用唯一 `case_id`，并记录：

| 字段 | 要求 |
| --- | --- |
| `case_id` | 稳定、可引用的 ASCII 标识（如 `sun-interval-01`），不能依赖临时文件名 |
| `reference_id` | 基线 ID 与 EXE/资源包指纹 |
| `setup` | 关卡、初始阳光、植物/僵尸位置、窗口与显示参数 |
| `input_sequence` | 带相对时间或视频帧号的有序输入；注明按下、释放和重复策略 |
| `observation_window` | 起止条件、时长、录制帧率和时间来源 |
| `repetitions` | 有效重复次数、失败次数及排除理由 |
| `observations` | 每次可见事件、帧号/时间、位置或状态 |
| `uncertainty` | 帧量化、输入延迟、窗口捕获和人工判读误差 |
| `classification` | `observed`、`inferred` 或 `development_parameter` |
| `acceptance` | 是否足以更新规则；不足时写明缺口 |

视频帧率不能直接当作模拟 tick 频率。若只能得到帧级区间，结果保留区间和误差；不得用平均值掩盖离散的事件顺序或边界差异。

## 从证据到规则

只有满足目标版本一致、控制变量固定、至少三次有效重复、误差小于规则所需分辨率、结果无矛盾且有原始证据索引时，参数才可从 `development` 候选升级为已测量规则。更新时必须同步 `content/levels/development-day.json` 或新的规则版本、`pvz-data`/`pvz-core` 验证、回放案例、行为基线和路线图；不能静默替换开发参数。

测量结果分为三类：

- `observed`：窗口中直接可见且重复稳定的事实，例如余额变化、生成时刻区间或失败画面。
- `inferred`：由多个观察推导的候选模型，例如碰撞边界或阶段先后，必须保留推导过程并继续标注不确定性。
- `development_parameter`：仅用于重写内部确定性和性能基线的值，不代表原版规格。

当测量结果改变 tick、输入、规则或回放合同时，先补充失败回归，再更新版本或兼容策略；保留旧证据和旧开发回放，禁止用最终胜负相同替代逐 tick 状态与事件比较。

## 验收输出

阶段完成时提交一份公开结果页和一份本机证据索引，列出已测量、候选推断、仍未知的参数以及每个参数的下一步。核心验收至少包括固定输入的 tick/事件顺序、阳光产出、豌豆发射/命中、僵尸啃食、割草机、失败/胜利、暂停/恢复和重开；实际窗口验收与 `pvz-core` 无资源回放分别报告，不能互相替代。

本设计不预建通用测量 CLI、持久回放格式或新的 package。只有存在稳定消费者、能在后台运行并减少重复工作时，才在后续计划中引入工具或数据格式；引入后仍须按 L1/L2 反馈层级验证。

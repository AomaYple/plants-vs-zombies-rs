# 原版行为基线测量设计

初始日期：2026-10-12；2026-10-13 更新任务依赖与规则采纳边界。本文定义已核对 EXE 与 `main.pak` 的可观察行为测量合同，为开发切片提供可追溯的规则证据；原版程序不作为运行依赖，新写 Rust 实现与原版资源/行为参考保持分离。

## 目标与边界

当前重写已经有可玩的白天开发切片和版本化原创 JSON，但其 60 tick/秒、间隔、碰撞盒和阶段顺序仍是开发参数。下一阶段只测量能由原版窗口、输入和连续画面可靠观察的事实，并把足够重复的结果转换为规则合同与回归案例。原版内部 RNG、私有事件和不可见状态只能标为推断，不能由截图直接声称已知。

首个教程重复验证测量入口；后续案例依赖各自的场景、时间/位置精度和控制条件，无关案例之间不设整批通过门槛。完整内容、动态动画、MO3、移动平台和发布打包不属于本测量合同；其中不依赖未知原版参数的工作可以独立开发，不能冒充原版还原验收。

## 双轨推进与依赖边界

证据轨先完成冒险 1-1 教程种植案例的身份、连续画面、固定输入、三次独立有效重复和证据索引，再扩展真实规则测量。入口失败只阻塞原版捕获和依赖其结果的规则采纳；有明确开发合同、能隔离并独立验收的测试、表现与平台工作继续推进。

一个案例合格即形成可审阅结果，采纳只等待它实际依赖的证据和核心表达能力。可见间隔按真实时间区间报告；无法唯一识别的模拟 tick 不阻塞其他事实记录，但不能无依据地将秒数转成原版 tick。可见事件顺序只报告捕获分辨率能区分的范围；内部顺序无法确定时保持未知。

反馈层级、检查复用和构建隔离统一见[贡献指南](../../../CONTRIBUTING.md#反馈层级)；任务调度及阻塞处理见[实施计划](../plans/2026-10-12-reference-behavior-measurement.md#调度与阻塞处理)。只为已有消费者引入工具与格式，不预建通用 CLI、持久回放格式或新的 package。

## 参考身份与控制变量

每组记录必须包含参考基线 ID `goty-zh-a7ab7df8-7f1e824e`、EXE 与 `main.pak` SHA-256、操作系统、窗口尺寸、显示缩放、输入设备、关卡/用户状态和采集日期。一次重复内绑定同一自有进程/窗口；跨重复可重启，但记录生命周期并重新建立同一初始状态和资源状态。输入序列、观察条件与捕获配置固定；改变变量时新建独立案例并说明原因。

原版截图、录屏、存档、窗口元数据和临时脚本写入被忽略的 `artifacts/` 或仓库外，不进入 Git、CI 或发行包。公开文档只保留可复核的文本结果、参数表、误差和证据索引。一次观察只能证明一次观察到的范围；至少三次独立重复才能作为候选稳定事实，随机或边界行为需要更多重复和明确的离散结果。

## 测量记录合同

每个案例使用唯一 `case_id`，并记录：

| 字段 | 要求 |
| --- | --- |
| `case_id` | 稳定、可引用的 ASCII 标识（如 `sun-interval-01`），不能依赖临时文件名 |
| `reference_id` | 基线 ID 与 EXE/资源包指纹 |
| `setup` | 关卡、初始阳光、植物/僵尸位置、窗口与显示参数 |
| `input_sequence` | 带相对时间或视频帧号的有序输入；注明按下、释放和重复策略 |
| `observation_window` | 起止条件、时长、录制帧率和时间来源 |
| `repetitions` | 有效重复次数、失败次数及排除理由 |
| `observations` | 每次可见事件、帧号/时间、位置或状态 |
| `uncertainty` | 帧量化、输入延迟、窗口捕获和人工判读误差 |
| `evidence_index` | 每次重复独立的文件索引、完整性指纹、帧/时间范围和引用的身份报告；共用环境信息可引用，但不能共用一次重复充当多次 |
| `classification` | `observed`、`inferred` 或 `development_parameter` |
| `acceptance` | 是否足以更新规则；不足时写明缺口 |

视频帧率不能直接当作模拟 tick 频率。若只能得到帧级区间，结果保留区间和误差；不得用平均值掩盖离散的事件顺序或边界差异。

事件时间以“上一帧未发生至下一帧已发生”的区间记录；时间源注明墙钟和单调时钟，附单次捕获起止时间、帧号、缺帧与重复帧。起止事件各有误差时保留完整间隔范围；捕获停更或缺少关键帧不能靠平均值补齐。教程余额是离散可见值，无法证明精确变化时刻，也不自动提供其他动态案例所需精度。

### 重复、有效性与排除

一次重复只有在以下条件全部满足时才计入有效重复：参考 ID、EXE 和 `main.pak` 指纹一致；目标进程由本次记录独占并能绑定到目标窗口；场景、用户状态、初始资源、窗口和显示参数与案例设定一致；输入序列完整且顺序可核对；观察窗口的起止条件满足，并取得能识别目标窗口的连续证据。重复之间必须重新建立同一初始状态，不能把同一段录像或同一帧的重复采样当成独立重复。

以下情况单独记为失败或排除，不计入有效重复：目标窗口无法唯一识别；捕获画面来自其他窗口、覆盖层或无法确认的来源；启动、输入、切场景或恢复过程中缺少关键帧；用户状态、初始阳光、卡片、位置或暂停状态与设定不一致；发生未记录的额外输入、失焦、最小化、弹窗或进程重启；时间戳、帧号或文件索引不完整。失败记录保留原因和证据位置，修正后必须从新的独立重复开始。

规则候选至少需要三次独立有效重复；随机行为、边界行为或存在离散顺序差异时，增加重复次数并报告散布。未达到这个门槛的记录仍可证明入口或单次可见事实，但不能升级为原版规则，也不能替换 `pvz-core` 的开发参数。

## 从证据到规则

只有满足目标版本一致、控制变量固定、至少三次有效重复、误差小于规则所需分辨率、结果无矛盾且有原始证据索引时，参数才可从 `development` 候选升级为已测量规则。更新时必须同步 `content/levels/development-day.json` 或新的规则版本、`pvz-data`/`pvz-core` 验证、回放案例、行为基线和路线图；不能静默替换开发参数。

观察分类与采纳状态分开：`observed`/`inferred` 描述来源性质，候选/已采纳描述是否进入实现。单次直接可见事实可以记录为 `observed`，但未达到接受条件仍不得采纳为稳定规则。部分字段有证据不意味着整个关卡已还原，教程与特定场景参数不能推广到全部关卡。

当前 `ContentBasis` 只提供 `Development`，schema 1 使用整个关卡的 `basis`，core 仅接受规则 2.0。首次实测采纳必须以实际参数为消费者，设计可区分开发字段与实测字段的来源及案例索引，明确内容/规则版本与旧输入的兼容或拒绝策略，并完成严格解析、装配和错误回归；不能只把 JSON 改成尚不支持的字符串。规则不变的来源补充与行为改变分别说明，不机械升级无关版本。

测量结果分为三类：

- `observed`：窗口中直接可见的事实，例如余额变化、生成时刻区间或失败画面；是否重复稳定、是否可采纳另按有效重复和接受条件判断。
- `inferred`：由多个观察推导的候选模型，例如碰撞边界或阶段先后，必须保留推导过程并继续标注不确定性。
- `development_parameter`：仅用于重写内部确定性和性能基线的值，不代表原版规格。

当测量结果改变 tick、输入、规则或回放合同时，先补充失败回归，再更新版本或兼容策略；保留旧证据和旧开发回放，禁止用最终胜负相同替代逐 tick 状态与事件比较。

## 验收输出

每个独立结果及时追加现有参考基线及本机证据索引，列出已测量、候选推断、仍未知的参数与下一步，不另建重复结果页。整体测量验收覆盖固定输入、时基、阳光产出、豌豆发射/命中、啃食、割草机、波次、失败/胜利、暂停/恢复和重开。核心逐 tick/事件回放、原版实际窗口与开发切片平台实跑分别报告，不能互相替代；尚未能确定的内部算法继续明确保留。

本设计不预建通用测量 CLI、持久回放格式或新的 package。只有存在稳定消费者、能在后台运行并减少重复工作时，才在后续计划中引入工具或数据格式；引入后仍须按 L1/L2 反馈层级验证。

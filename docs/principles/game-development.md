# 游戏开发原则

游戏开发原则约束这个项目如何重新实现和还原 Plants vs. Zombies。它们描述开发效率、游戏运行时和资源边界，不把尚未测量的原版事实写成规格。当前已核对的文件指纹和待验证行为见 [参考基线](../behavior/reference-baseline.md)。

## 重写范围与参考边界

- 这是独立的 Rust 全量重写。游戏逻辑、动画播放器、渲染、音频接线、关卡系统、存档和工具都重新实现，不复用原版程序代码；使用成熟依赖遵循工程原则中的评估要求。
- 原版 EXE 只用于本机行为观察和身份核对，不作为重写游戏的运行依赖。原版资源和 `main.pak` 只作为用户本机的资源输入或核对材料。
- 参考基线以实际文件指纹、读取结果、运行观察和可重复测量为准。目录名、媒体标签、讨论中的建议值和单次截图不能单独证明版本、规则或时序。
- 当新测量与旧结论冲突时，保留旧证据，记录差异和适用范围，不静默改写基线。

## 游戏开发效率

- 在保持行为还原、确定性、平台契约与质量门槛的前提下，尽可能缩短游戏功能从开发到验证的迭代周期。
- 优先复用已验证的项目模块、成熟依赖、原创夹具和回放；用清晰接口与经过确认的数据规则减少重复实现和内容扩展成本，抽象和工具依据实际重复工作引入。
- 围绕可独立验收的小功能增量推进，及早验证资源、规则与平台接入；开发中先运行相关测试，用必要的自动化和可安全并行的检查缩短反馈，提交前完成全部适用验收。
- 根据实际反馈耗时和返工原因改进构建、测试、资源接入与内容开发流程；开发效率的提升必须保留有效测试、覆盖率要求与原版行为核对。

## 运行时分层

- 数据、模拟、资源和平台表现按职责分层，模块接口与依赖方向在架构文档中维护；资源解析与模拟核心不互相依赖，由应用层装配。
- `pvz-core` 保持纯 Rust，不依赖 Macroquad、资源解析、操作系统 I/O、设备输入、音频、资产路径或墙钟时间。
- 资源层输出 CPU 侧模型与诊断，GPU、音频和平台 I/O 由应用适配；宿主机资源工具不加入 Web 应用依赖图。
- 伤害、阳光、波次、碰撞和胜负由核心决定，平台和表现层不能复制一套隐藏规则。

依赖方向和数据流以 [架构文档](../architecture/README.md) 为准：平台输入转换为带顺序的命令，核心按固定模拟时钟更新状态和事件，动画、渲染和音频消费这些结果。

## 确定性与行为还原

- 模拟时钟、动画时钟和渲染时钟分离。动画资源中的 fps 不能直接当作模拟 tick 或全局规则时钟。
- 固定规则版本、初始状态、RNG 算法与 seed，以及带 tick 序号和确定顺序的命令后，状态摘要和事件序列必须可重复；不要求重写实现采用原版内部随机算法。
- 伤害、阳光、波次、碰撞、死亡、胜负、暂停和重开由模拟核心决定；表现层只能消费状态和事件，不能反向改变规则。
- 事件顺序、命令顺序和回放结果属于行为合同。性能优化、平台适配和渲染替换都必须保护已经验证的合同。
- 原版行为按观察、控制变量和回放测试逐步确认；尚未测量的 tick、碰撞盒、随机数算法、资源轨道含义和输入区域保持待验证状态。

## 坐标、渲染与资源表现

- 逻辑坐标、碰撞盒和模拟规则与物理视口分离。输入先从窗口或触摸坐标反变换到逻辑坐标，再生成游戏命令。
- 2K 和 4K 模式在实际视口分辨率绘制，保持逻辑布局和碰撞规则稳定；高 DPI、缩放、裁剪和背景偏移属于表现层合同。
- 原版低分辨率素材可以通过整数或高质量缩放、插值、裁剪和布局适配高分辨率屏幕，但不能凭空恢复素材中不存在的细节，也不能以高清替换素材改变碰撞或规则。
- 资源缺失、路径大小写冲突、编码错误、未知轨道和不支持的格式必须显式报告；不能静默换用占位资源或改变显式配置。
- Linux 等大小写敏感平台必须单独验证资源索引和路径碰撞，不能因 Windows 目录可加载就假设所有平台都可加载。

## 跨平台目标

支持目标包含 Windows、macOS、Linux、Web、Android 和 iOS。推进顺序是桌面与 Web 先行，Android 与 iOS 随后接入。

- 核心模拟和资源模型尽量保持平台无关。
- Windows、macOS、Linux 需要分别验证窗口、输入、文件路径、音频、存档和打包。
- Web 需要分别验证 WebAssembly 构建、浏览器资源加载、输入、音频手势和浏览器存储；宿主机资源工具不随应用进入 Web。
- Android 和 iOS 需要分别验证触摸、生命周期、应用数据目录、资源包和平台打包；iOS 还需要在 macOS/Xcode 环境完成实际验收。
- “支持”必须对应目标平台的构建与最小运行证据；crate 能编译不等于平台已经支持。

## 原版资源与公开边界

- 原版资源、截图、录像、EXE、`main.pak` 和派生资源留在仓库外或被忽略的本机目录，不进入 Git、CI 或发行包。
- 公开测试夹具必须原创、最小、可审阅并注明来源；不能把复制或改名后的原版文件当作测试数据。
- MIT 只覆盖本项目原创代码、文档和明确原创的测试数据，不授权原版素材、名称、商标或第三方依赖。
- 资源接入、忽略目录和本地路径配置遵守 [资源约定](../../assets-private/README.md)；公开发布前检查跟踪文件、历史、许可证和构建产物。

实现顺序和阶段验收见 [项目路线图](../roadmap.md)。在文档与结构阶段，不因为这些原则已经写入仓库就提前创建 Rust 源码或宣称游戏功能可用。

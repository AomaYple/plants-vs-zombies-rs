# 工程原则

工程原则约束项目的开发方式和交付质量。它们适用于文档、工具、Rust package、CI 和公开仓库；具体命令与当前阶段的验收顺序见 [贡献指南](../../CONTRIBUTING.md)。

## 正确性与证据

- 正确性是性能优化与开发提效的前提。先保护行为、边界和错误处理，优化时保持必要的测试与验收门槛。
- 区分规划、静态检查、构建、测试、实际运行、平台验收和原版行为比对；没有执行的检查不能写成通过。
- 每个重要结论都应能追溯到文件、命令、测量结果或明确的外部证据。推断、暂定值和待验证项要显式标记。
- 改动聚焦一个可审阅的目的；发现接口、配置或阶段发生变化时，同步相关设计、计划、决策记录和验证说明。

## 现代 Rust 与仓库结构

- 遵循当前 stable Rust 的现代实践，以 `rust-toolchain.toml`、`Cargo.toml` 和实际 CI 配置为准；不因为“现代”而未经验证地升级工具链或依赖。
- 使用标准 Cargo 布局和命名：package 与包目录采用小写 kebab-case，Rust 模块、函数和源文件采用 snake_case，类型采用 UpperCamelCase；保留 `README.md`、`AGENTS.md`、`CONTRIBUTING.md` 等标准文档名。
- 模块按职责和实际消费者拆分；不为“以后可能使用”预建空 package、占位模块或无用途目录。
- 公开 API 保持最小，用类型表达 ID、版本和约束，说明错误及必要的所有权约定；不为测试便利扩大可见性。
- 可预期的解析、输入和 I/O 失败返回明确的 `Result` 与上下文；未知格式和不支持的能力必须产生可读诊断。
- 项目代码遵循 workspace 的 `unsafe_code = "forbid"`；第三方依赖单独评估用途、兼容性、维护成本、可复现性、许可证和安全公告。
- 通过 rustfmt、编译器、Clippy、rustdoc 和依赖审计检查实现质量。首次注册 package 时提交 `Cargo.lock`、显式继承 workspace lint 并同步实现阶段 CI；具体操作与命令见贡献指南。

## 测试与覆盖率

- 尽可能增加适用且有意义的测试类型，覆盖不同接口、行为与风险；具体类型和选择依据见测试策略，解析器按风险补充模糊测试。
- 功能或规则变更先建立测试；缺陷修复必须补充能够在修复前发现该缺陷的回归测试。
- 测试默认并行。每个测试隔离输入、临时目录和状态；确实无法隔离时，只对最小范围串行并记录原因。
- 尽可能提高有效覆盖率，持续补齐核心规则、边界条件、错误分支和平台契约。覆盖率用于发现遗漏，不用无意义断言、排除关键代码、忽略失败或降低门槛制造通过。
- 使用固定 seed、初始状态和命令验证确定性；公共测试夹具必须原创、最小、可审阅并记录来源，不能复制原版资源。
- `cargo llvm-cov` 的结果要说明测量范围、feature 组合和遗漏，暂未覆盖的关键路径记录原因与补测安排；门槛基于真实基线，不预设无依据的百分比。覆盖率不替代测试设计、基准和目标平台实际运行。

详细测试层级、隔离要求和夹具边界见 [测试策略](../testing/README.md)。

## 性能与资源使用

- 在正确性得到保护的前提下，尽可能提高运行速度、降低延迟与内存占用；依据实测瓶颈确定优化顺序。
- 核心数据结构、资源解析和高频路径随实现提供可重复的 Criterion 时间基准；涉及内存与分配的变更补充相应测量。
- 基准固定工具链、编译配置、输入规模、seed、规则版本和测量环境；分别记录耗时及其离散度、适用的内存与分配指标，以及优化前后的行为验证结果。
- 时间与空间存在取舍时，记录适用负载、收益、代价和选择依据；用同条件测量判断整体效果。
- 优化前先有正确性和回放测试，优化后重跑行为、事件顺序、回放和性能验证；性能提升不能改变已确认的可观察行为。

详细测量边界见 [性能策略](../performance/README.md)。

## 代码与仓库卫生

- 所有可读文本使用 UTF-8、LF、无 BOM，文件末尾保留换行；二进制保持原始格式并记录用途和来源。
- 不保留或提交死代码、未使用依赖、未使用导入、无效配置、无实际用途的空实现、未接入占位分支或无用途文件。
- 按受支持的 target 和 feature 组合运行编译器与 Clippy，并在评审中核对实际调用方；不能仅凭没有 lint 警告判定不存在死代码。
- 不通过无意义的 `pub`、无依据的 `allow`、删除有效测试或放宽检查掩盖问题。
- 保护凭据、个人路径、缓存、构建产物和不应公开的本地证据；提交前检查跟踪文件、Git 历史和忽略规则。

## 跨平台工程

- 平台差异收敛到明确的适配层；选择依赖和接口时评估 [游戏开发原则中的全部支持目标](game-development.md#跨平台目标)，不能只因一个平台构建成功就宣称完整支持。
- 每个平台分别记录目标、工具链、构建命令、运行结果、限制和未验证项。Web 构建要区分应用与宿主机工具；移动平台需要记录触摸、生命周期、存储和打包验收。

## Git、评审与交付

- 本地 `main` 保持稳定，使用短期分支，一个分支围绕一个可审阅目的；代理新建分支默认使用 `codex/` 前缀。
- 提交遵循 Conventional Commits：`type(scope): 中文说明`。type、scope 和技术名称保留标准写法，标题和正文使用中文。
- 提交前检查工作区、暂存差异、文件来源和适用验证；提交不包含凭据、缓存、构建产物或无关改动。
- PR 说明问题、最终行为、验证命令和结果、限制以及必要迁移；评审意见针对可核查的行为和契约。
- 推送、PR、合并、打标签和发布按当次明确授权执行；共享历史的改写需要单独授权。

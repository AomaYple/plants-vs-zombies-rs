# 工程原则

工程原则适用于文档、工具、Rust package、CI 和公开仓库，与 [共同原则](README.md#共同原则)一起执行。具体命令与阶段验收见 [贡献指南](../../CONTRIBUTING.md)。

## 正确性与证据

- 围绕实际接口、行为和风险确定验收条件；检查应能发现目标问题，失败须解决原因。未执行的必要检查不算通过，缺少环境须记录影响范围与待验收项。
- 重要结论能追溯到文件、命令、测量或外部资料，并说明验证范围。原始证据按来源契约保留；推断与暂定值不写成已确认事实。
- 改动聚焦一个可审阅目的；接口、配置或阶段变化时同步相关文档和验收，保留其他任务的改动。

## 现代 Rust 与仓库结构

- 遵循当前 stable Rust 的现代实践，使用仓库固定的工具链；升级编译器或依赖时验证兼容性、可复现性与受影响平台，并同步配置和 CI。
- 使用标准 Cargo 布局和命名：package 与包目录采用小写 kebab-case，Rust 模块、函数和源文件采用 snake_case，类型采用 UpperCamelCase；保留 `README.md`、`AGENTS.md`、`CONTRIBUTING.md` 等标准文档名。
- 模块和目录按职责、实际消费者与生命周期拆分。文档阶段的预留目录只有在有明确用途说明、后续入口或验收目的时才保留；开始实现时只注册有源码入口和验收目的的 package，不预建无用途模块、package 或目录。
- 公开 API 保持最小，用类型表达 ID、版本和约束，说明错误及必要的所有权约定；不为测试便利扩大可见性。
- 可预期的解析、输入和 I/O 失败返回明确的 `Result` 与上下文；未知格式和不支持的能力必须产生可读诊断。
- 项目代码遵循 workspace 的 `unsafe_code = "forbid"`；第三方依赖单独评估用途、兼容性、维护成本、可复现性、许可证和安全公告。
- 能满足项目合同的通用能力优先采用成熟库和已有实现，不重复编写已有可靠方案的逻辑。项目自写代码集中于游戏领域规则、资源语义和必要适配；确需自行实现通用能力时，说明现有方案为何不能满足正确性、兼容性或实测性能需求，并交付相应验证。采用库仍须遵守依赖评估和架构边界。
- 首次注册任何 package 时提交 `Cargo.lock`、显式继承 workspace lint，并启用实现阶段的格式、检查、测试、Clippy、文档与依赖审计；之后依赖变更同步锁文件，验收保持锁定。

## 语言与说明文字

- 项目自写的文档正文、任务与验收说明、注释、贡献说明、表单提示、显示名称和自定义诊断信息使用中文；注释重点说明原因和契约。
- 技术名称、人员署名、文件与目录名、crate 名称、代码标识符、命令、配置键、格式枚举值、资源 ID 和标准提交标记保留原写法，不为中文化改变机器接口。
- 标准 MIT 许可证正文、第三方原文和原版资源中的文字、标签与署名按来源契约保留；引用外部原文时标明来源，并用中文解释需要说明的内容。工具或依赖自身产生的输出不要求改写。
- 新增或修改说明文字时核对同一概念的译法，并同步受影响的入口、模板、计划与诊断；不通过添加重复译文或无用途文件实现语言统一。

## 测试与覆盖率

- 尽可能增加适用且有意义的测试类型，覆盖接口、行为、边界、错误分支和平台风险；测试类型与选择方法见 [测试策略](../testing/README.md)。
- 功能与规则变更随实现交付适用测试，已明确的行为优先测试先行；探索性工作可先用探针获取证据，进入正式实现与交付前补齐测试。缺陷修复补充能捕获原缺陷的回归测试，文档与配置改动验证相应合同。
- 测试默认并行。每个测试隔离输入、临时目录和状态；确实无法隔离时，只对最小范围串行并记录原因。
- 编译、测试、性能测量、服务和应用运行尽可能全程在后台进行，不抢焦点、不切换前台，减少与维护者使用电脑的冲突。优先采用隔离进程、隐藏窗口和后台浏览器；确实无法在后台完成的真实窗口或交互验收，才使用最小范围的前台操作，并说明原因。后台执行仍须保留可核查的结果，不以无头检查替代必要的实际运行证据。
- 尽可能提高有效覆盖率，持续补齐核心规则、边界条件、错误分支和平台契约。覆盖率用于发现遗漏，不用无意义断言、排除关键代码、忽略失败或降低门槛制造通过。
- 测试输入可复现，公共夹具原创、最小、可审阅且注明来源；确定性合同见 [游戏开发原则](game-development.md#确定性与行为还原)。
- 覆盖率随相关实现接入，报告测量范围、target/feature 组合与遗漏；暂未覆盖的关键路径记录原因和补测安排，门槛依据真实基线。覆盖率不替代测试设计、基准和目标平台运行。

## 性能与资源使用

- 在正确性得到保护的前提下，尽可能提高运行速度、降低延迟与内存占用；依据实测瓶颈确定优化顺序。
- 核心数据结构、资源解析和高频路径随实现建立代表性、可重复的时间基准，复用已有场景并按覆盖缺口补充；工具与测量方法在 [性能策略](../performance/README.md)维护。
- 改变关键路径的内存布局、分配策略，或声称内存改善时，补充相应测量；其他变更依据实际性能影响与风险选择检查。
- 用同条件测量比较优化前后，记录受影响场景的耗时、内存与分配指标、环境和时间/空间取舍。
- 优化前建立正确性保护，优化后重跑相关行为、边界、错误处理、事件顺序和回放检查；性能收益必须与行为验证一起报告。

## 代码与仓库卫生

- 所有可读文本使用 UTF-8、LF、无 BOM，文件末尾保留换行；二进制保持原始格式并记录用途和来源。
- 保持代码与仓库结构最小、可解释且可维护：不保留死代码、未使用依赖/导入、失效配置、无实际用途的空实现、文件或目录。每个被跟踪的文件和目录都应有明确的消费者、生成入口、验收目的或文档职责；结合编译器、Clippy、有效 target/feature 组合和实际调用方核对，不能通过无意义的 `pub`、无依据的 `allow` 或删除有效测试掩盖问题。
- 删除或移动文件、目录或模块前检查调用方、测试、配置、文档和生成入口；过时测试与配置随合同变更更新或移除，并记录依据。
- 保护凭据、个人路径、缓存和构建产物；版本化原版资源、原创夹具和本机派生产物分别遵守 [公开边界](game-development.md#原版资源与公开边界)与资源清单约定。

## 跨平台工程

- 依赖和接口评估全部 [平台目标](game-development.md#跨平台目标)，按实际支持的有效 target/feature 组合建立检查矩阵；互斥组合分别验证，不以一次全开替代矩阵。
- 平台相关变更验收受影响的已支持范围，未来平台记录兼容性与待接入事项；不把尚未实现的平台写成已通过，也不要求无关变更重复六个平台的实机验收。
- 构建与运行分开记录，附环境、命令、结果、限制及未验证项；实际平台验收按贡献指南执行。

## Git、评审与交付

- 本地 `main` 保持稳定，使用短期分支，一个分支围绕一个可审阅目的；代理新建分支默认使用 `codex/` 前缀。
- 提交遵循 Conventional Commits：`type(scope): 中文说明`，scope 可省略；描述与正文使用中文，type/scope、技术名称和标准 footer 标记保留原写法。具体格式见贡献指南。
- 提交前检查工作区、暂存差异、文件来源和适用验证；提交不包含凭据、缓存、构建产物或无关改动。
- PR 说明问题、最终行为、验证命令和结果、限制以及必要迁移；评审意见针对可核查的行为和契约。
- 自动化代理的推送、PR、合并、打标签、发布与共享历史改写按用户授权执行；已有远端或此前一次操作不扩展到后续动作。
